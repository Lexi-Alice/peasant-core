# Skill and Notable Editor Plan Audit

September 7, 2026. Read-only source inspection and isolated Node probes; corrections applied to the plan and design documents only. No application code, real actor data, or live world was modified.

Amended September 9, 2026 after design approval: the earlier Source Kind/Source link and inherited-field model is intentionally removed from the roadmap. It is replaced by direct, fixed-list Weapon Type and Gate Type classifications with a Custom option. These fields do not link entries or inherit mechanics. Type `Standard` is renamed to `Skill` internally and visibly; version 10 migrates both actor collections and changes legacy `Other` to the Custom path without rewriting authored non-list Type names. The later approved Category matrix limits fixed Type options, shows Weapon Type only for Martial Skill and Gate Type only for Magic Gate, and uses migration version 11 to replace existing mismatched built-in Types with each Category's default without rewriting authored non-list Custom names. Signature is then promoted to a Martial/Tradewrite/Mundane Type with Skill-like progression and roll fields; Martial Signature also shows Weapon Type. Version 12 replaces the former Type on permitted or unclassified `sig:true` entries, while Magic retains its valid Type and clears Signature. The shared editor and Notable lists remove Signature checkboxes; the Skills list retains its checkbox only as a stable-ID Skill/Signature Type shortcut.

Amended September 10, 2026 after design approval: Magic replaces Skill with Spell followed by Subskill. Spell keeps Skill-style Class, Rank, To-Hit, and Accuracy, gains Gate Type, and remains ineligible for the Skills-list Signature shortcut. Subskill is identity-only in this header and hides progression, roll, Weapon Type, and Gate Type controls. Version 13 converts existing Magic Skill entries to Spell in Skills and Notables while preserving Gate Type and sibling data.

Further amended September 10, 2026 after design approval: Martial replaces Skill with Weapon and adds Defense and Combat Trick. Weapon, Defense, Combat Trick, and Signature remain rollable Class/Rank types but show distinct Weapon Type, Defense Type, Trick Type, or Martial-only Signature Type selectors. Defense Type is Block/Parry/Dodge/Armor; Trick Type and Signature Type combine the Weapon and Defense lists; all end with Custom. Version 14 migrates Martial Skill to Weapon, seeds blank Martial Signature Type from Weapon Type without clearing it, and removes legacy `sig`. The previously retained Skills-list Signature checkbox is now removed; Type is the only Signature control.

Also amended September 10, 2026 after design approval, then corrected September 13 during implementation: Characteristic Mode is hidden and normalized to Single for zero or one selection. With two or three selections, the selector contains Mixed and Advantaged; with all four, those same stored modes are labeled Omni Worst and Omni Best without a migration. Missing, legacy, or Single mode normalizes to Mixed. Characteristics and mode must be saved together so adding or removing the threshold checkbox cannot retain an invalid hidden mode. All four Characteristic choices remain on one compact horizontal row, with Mode, To-Hit, and Accuracy top-aligned beside them without clipping at the 560px minimum width. In Skills, Usage/options and AP/SP share the following compact row; in Notables, Usage remains separate.

The Skill/Notable editor separators below the identity header and below the primary tabs follow the equipment-card tab-border token. There is no separator above the primary tabs. The visual emphasis comes from the shared stronger border color rather than a separate thickness or new theme value.

Signature counters use the standard character-sheet `pc-foundry-section` fieldset and a `Signature Uses` legend. This replaces the editor-specific faint counter border while preserving the existing compact controls and horizontal wrapping behavior. An editor-scoped counter rule overrides Foundry's higher-specificity `.standard-form fieldset` column/no-wrap layout and large spacing, which would otherwise turn the counter area into a tall vertical stack. Every Current/Maximum numeric input remains 72px wide. The Duress field wrappers use their labels' intrinsic width instead of a fixed width, reducing space within the Duress Current/separator/Maximum group without truncating either label. Their unchanged 72px inputs are left-aligned beneath those labels, explicitly capped at 72px against the editor's general `width: 100%` input rule, and use 4px horizontal padding. The `Duress Uses` checkbox label is content-sized instead of flex-growing, with a 3px internal gap, so it does not insert unused space before the Duress count group.

The configurable Signature counter label and recovery/note are retired from the UI and data model. World migration version 15 removes `signatureUsage.label` and `signatureUsage.note` from both actor collections while retaining Current/Maximum, Duress state, and unrelated metadata. Normalization also strips these fields so imported or subsequently encountered legacy entries cannot restore them.

Amended September 11, 2026 after design approval: the optional counter switch is labeled `Duress Uses` and its canonical stored boolean is `signatureUsage.duressUses`. World migration version 16 transfers both true and false values from legacy `signatureUsage.duressEnabled`, removes the old key, and preserves `duressCurrent`, `duressMax`, and sibling metadata. Pre-schema and current-entry normalization apply the same compatibility rename to later legacy imports.

Also amended September 11, 2026 after design approval: Details tags sit inside a Foundry-style fieldset whose `Tags` legend copies the native Scene Levels control and placement: a `control` legend with a regular square-plus `icon inline-control` immediately after the title at a 4px gap. It opens the existing chooser; the separate toolbar, large Add Tag button, and Add Group control are removed. The list follows the established inventory/notable/effects pattern: one shared bordered panel, a dark `Tag` / `Summary` header band, and compact contiguous rows separated by thin dividers. On hover, focus, or while expanded, a tag row mirrors the Description/Details/Effects tabs by applying their light text and red glow to only the disclosure chevron and canonical tag name. It draws no orange row outline and does not highlight the mechanical summary or options menu; the summary button's native outline remains suppressed because the name-and-chevron glow is the visible focus state. The existing edit draft remains the expandable body and appears as a full-width subrow directly beneath its selected row without a card gap or border seam; its padding and internal gaps are reduced, and its mechanical controls begin immediately without an `Edit Tag:` or `Add New Tag:` heading. In both Skill and Notable editors, the open row now collapses on a second click and discards its unsaved draft through the former Cancel path; the visible Cancel button is removed while Escape remains available. Display Name and Note / Limit are retired from every tag editor and layout schema. Version 17 clears their `label` and `note` keys from top-level, base-usage, and alternate-usage layouts in both actor collections while preserving Custom tag names, values, IDs, menus, and ordering. Version 18 removes all stored organizational group rows from those same layout scopes while retaining the tag rows in their existing order.

Also amended September 13, 2026 after design approval: the Usage Notes editor is removed from the Details panel and its stored base-usage and alternate-usage `description` fields are retired. Version 20 removes those nested descriptions from both Skills and Notable Combats while preserving entry-level descriptions and all other usage data. Normalization and the actor data schema no longer expose or recreate usage descriptions.

The approved compact spacing removes the first tag row's top divider, resets inherited tag-list padding and minimum height to zero, and gives every tag row the same 38px minimum height. The Tags fieldset uses 10px top padding, the open Add Tag chooser uses a 4px top margin beneath that outer legend, and the nested browser adds no top margin, keeping the controls compact and eliminating the false extra height beneath the final entry.

Expanded tag mechanics now favor one wrapping row wherever their controls fit: Damage and Heal combine dice and Type; Speed combines its selector and conditional Max Uses; Manifest Dome and Manifest Resistance combine dice with Duration or HALT; and Custom combines Name and Value. Shared compact tag selectors use a stable responsive width equal to 25% of the available row, bounded from 120px through 140px, so they expand with the editor without responding to option text length. Resource Costs keeps one compact row per resource and leaves a small Add Cost action beneath the rows. The expanded input area no longer carries the legacy minimum height or vertical padding. Existing single-field tags remain single-line, Strengthen's guidance is one sentence, and Defense remains sectioned. This is presentation-only and preserves every collector, conditional control, and stored value.

The shared Skill and Notable editor remains resizable but now matches the equipment-window width by enforcing a 560px by 420px minimum whenever it is not minimized. Its existing internal scrolling keeps all editor content reachable at that floor.

The outer editor application also carries Foundry's `standard-form` class, whose 16px flex gap otherwise separates the title bar from the window content. A shared-editor-scoped override removes only that outer gap so its top spacing matches equipment windows; the existing 12px content padding and all form-internal spacing remain unchanged.

The approved Add Tag chooser has no visible Tag Type select. The title-adjacent square-plus reveals one searchable combobox inside a compact nested Foundry fieldset whose inline legend reads `Add Tag`, with `Search tags` retained as the input placeholder. The chooser remains modeled on Peasant Core's Active Effect change-key browser: focus or click shows the full fixed catalog, typing filters by visible label, and click or Arrow Up/Down plus Enter chooses a result. Escape, Tab, or moving focus away closes the dropdown. Selection keeps the established canonical tag type internally and opens the existing mechanical draft; unmatched text is not a new tag, and Custom remains the authored-name path. No stored tag shape or migration changes.

## Assessment

The selected UI direction remains sound. The initial plan was too broad to treat as a single UI change and underspecified some persistence, undo, and effect-lifecycle boundaries. It should be executed as three integration milestones, with the first producing a native-styled authoring demo and later milestones supplying the tested runtime behavior. Accepted capabilities remain in the roadmap except for the superseded source-link/inheritance model described above.

The following findings have been **addressed in the plan**, not fixed in the application. Sol must implement and verify their listed tests.

## Probe results

Two isolated Node probes imported the existing undo module and used an in-memory fake actor. They did not mutate workspace source or Foundry data.

```json
{
  "counterUndoPaths": ["system.skills"],
  "laterNameEditOverwritten": true,
  "newSkillEffectUndoRecords": 0
}
```

The counter probe captured a 2 → 1 Signature change, changed the Skill name afterward, then applied its undo record. The original name was restored, demonstrating the broader array replacement. The effect probe created only a Skill-type effect under includeSpellEffects and produced zero undo records. These are compatibility hazards the plan must handle before its new runtime behavior is considered complete.

Other findings came from tracing the actual source and plan contracts. No live Foundry UI, permission routing or template lifecycle was exercised during this audit. Full application tests were not run because this task changed documentation only.

## Recommended implementation sequence

1. **A: editor and data preservation.** Implement Tasks 1–4 with the actual Foundry styling, all identity fields, Signature Type/counts, and no Signature checkbox. Demonstrate Musket, Dome, First Aid and a Signature on disposable fixtures.
2. **B: usages and execution.** Implement Tasks 5–7, including explicit defaults, classification propagation, modifier snapshots, counter-leaf undo and actual Edge/Stress regression tests. Keep the two collections separate.
3. **C: effect offers and shortcuts.** Implement Tasks 8–9 with definition isolation, Skill-effect undo, preserved success/target context and native hotbar/link behavior. Finish Task 10's whole-system verification.

Do not remove the user's flexible layout, custom rules, characteristics, Accuracy, Category/classification identity or Signature counts to simplify the code. Simplify by reusing current controls/workflows and by separating the review milestones. Automatic family-pool accounting and arbitrary rules scripting remain outside this plan.

The plan's code snippets are focused contracts/assertions unless they include imports and a complete fixture. They are not evidence of runnable tests or implemented APIs. Sol must build actual fixtures using the verified existing test patterns and invoke real entrypoints, especially `applyEdgeChainRoll`, `applyEdgeIndividualDieRoll`, `captureActorRollUndo`, and `applyRollUndoRecords`; no test may pass by substituting a mock that already embodies the behavior it is supposed to verify.
